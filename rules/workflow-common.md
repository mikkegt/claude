# 開発ワークフロー（共通）

Mac / Ubuntu 両方に適用される共通ルール。OS 固有の厳しさ・緩さは `workflow-mac.md`
（Mac 厳格）と `workflow-ubuntu.md`（Ubuntu 緩め）に分けてある。

## Issue を立てる前に

`issue-draft` skill は対話的に同じ手順を踏む。手で立てるときも同じルールが要る。

- MUST 直近 20 件の issue を確認し（`gh issue list --limit 20 --state all`）、重なる
  ものがあるかを述べる。重複は議論を分散させ、ニアミスはたいてい「本当の問題は
  もっと大きい」という合図
- MUST コードの見た目からではなく、実際のコードを追って欠陥を確認してから立てる。
  見た目から論証した issue は、本番では到達できないケースのために修正を作らせる
- MUST handler だけでなく入力の producer を grep する。handler は見つけやすい半分で、
  推論の足場としては役に立たない半分
- MUST 到達可能性を示せないなら issue にしない。発見した PR の本文に、何を確認して何を
  確認できなかったかとセットで記録する。到達不能な issue は誰かの 1 日を消し、PR の
  1 段落はコストゼロで発見を残す

本文に書くこと:

- MUST 症状を観測したのか推測したのかを書き、確認できなかった点を名指しする。沈黙は
  「確認して問題なし」と読まれる
- MUST リグレッションか元からの欠落かを判定して書く。`git log -S'<存在するはずの文字列>'
  -- <path>` で該当コミットを探し、コミットメッセージを読む。意図的な削除はたいてい
  message にそう書いてある。判定は「誰かが壊した」と「最初から動いていない」を分け、
  担当と緊急度を変える
- MUST 閾値・上限・タイムアウトなど数値が争点なら、分離したい 2 集団を最悪値込みで実測し、
  修正対象のコードを読んでから提案する。平均は誤らせる（正常 1.92〜1.99 と異常 3.84〜3.91
  なら「3.5 に引く」と言いたくなるが、正常側に 3.57 の実測があれば引ける線は無い）

部分対応の PR に closing keyword を書かない:

- MUST issue の一部だけを扱う PR に `Closes #N` / `Fixes #N` / `Resolves #N` を書かない。
  文章で限定しても無駄で、GitHub はキーワードだけを解釈して周囲の文を無視する。
  `#N` か `refs #N` を使い、全フェーズが出荷されてから手で閉じる
- MUST 誤って閉じたら即座に reopen し、何が出荷され（マージコミット付き）何が残っているかを
  コメントする。黙って閉じた issue は、残りのフェーズが失われる経路

## PR 説明の作り方

- MUST 「背景」セクション（なぜこの変更が必要か）を含める。ユーザーの生のプロンプトを
  そのまま転記しない（Claude Code 生成マーカーの扱いは `git-mac.md` / `git-ubuntu.md` を参照）
- MUST AI が実装した PR は、説明の最上位に「Summary」節と「Items to Confirm / Review」節を
  置く。人間レビュワーが「何が変わったか」「何を特に見てほしいか（リスクある判断・仮定・
  未検証の挙動）」を最初に把握できる形にする。背景・実装詳細はその後
- SHOULD 設計変更・ドメインロジック変更・不具合の根本修正・方式選定・データ構造変更・
  パフォーマンス改善などの重い PR は、Context / Why / Decision / Alternatives / Risk の
  判断記録テンプレを本文に含める（推測で書かない。検討していない代替案は書かない）

## レビュー指摘の取り込み

レビュー指摘は「実装漏れを埋めてください」の形で来る。埋めること自体は正しくても、
埋めた結果として周辺の前提が崩れることに気づきにくい。指摘対応は差分だけ見ない。

- MUST 修正を入れる前に、その修正で PR 本文・設計メモの他の記述が嘘にならないか確認する。
  嘘になるなら本文も同じ PR で直す
- MUST 「スコープ外」「別 issue で検討」と宣言した項目を、修正のたびに読み直す。
  その修正でリスクの性質が「起こりうる」から「必ず起こる」に変わったら、スコープ外の
  判断は無効になっているのでスコープ内に戻す
- SHOULD 指摘が本文の記述と実装の食い違いを突いているとき、直すのは実装とは限らない。
  本文側（＝設計判断そのもの）が誤っている可能性を先に潰す

## 承認後に入ったコミットは承認の対象外

Approve は「その時点の HEAD」に対して出る。その後に積まれたコミットは誰にも見られていない。
リネーム・フォーマット・コメント追加のような「無害に見える機械的変更」ほど、
差分を読み流されるので危ない。

- MUST レビュー・マージの判断をする前に、最後の Approve 以降に積まれたコミットを確認する。
  0 件でなければ、その差分は未レビューとして扱う
- MUST 一括置換・リネームの差分は、変更後だけでなく **変更前と1行ずつ対応づけて** 読む。
  同じ型の識別子（添字、ID、ハンドル）同士の取り違えはコンパイルも lint も通る
- SHOULD 変更前後で挙動が同じはずの修正（リネーム、抽出、整形）ほど、
  それを保証するテストが無いなら手元で動かして確かめる。「変わらないはず」は検証ではない
- MUST 「挙動は変わらない」が主張の全部である変更（抽出、移動、削除、lint 一括対応、
  「単純化」）は、旧コードを逐語的に使い捨てのハーネスへコピーし、新コードと並べて生成
  入力で走らせ、比較した件数を添えて報告する。手順と、ハーネス自体が壊れて 0 件と出る
  失敗パターンは `refactor-safely` skill にある

関連: `verify-first-source.md`（「実装済み」と書く前に読む）

## 実装前の重複チェック

新機能を設計・実装する前に、隣接モジュールで似た実装が既にないかを必ず確認する。
「他メンバーが既に作った物と重複実装する」事故 (ソロ開発なら「過去の自分の実装を忘れて重複」)
を防ぐため。

- MUST 「既存の実装 (クラス名やファイル名) から想像しにくい機能」が中に埋まってる
  可能性を疑い、動詞 (`Resolve` / `Match` / `Select` / `Parse` / `Handle` 等) で
  関連モジュール全体を `grep` して網羅的に探す
  (例: `Reader` クラスの中に解決ロジックが埋まってる等)
- MUST 隣接モジュール (同ディレクトリ + 依存する他モジュール) の 公開 API に一通り目を通す
  (C/C++ ならヘッダ、TS なら `*.d.ts` や `index.ts`、Go なら公開関数の宣言、
  Python なら `__init__.py` や公開クラス)
- SHOULD 他メンバーの担当領域と自分の設計が重なる場合、着手前に本人に共有・確認する

見落として二重実装した場合、後から片方を採用/廃止/統合する追加コストが発生する。
grep + 公開 API 一読の 5〜10 分は、この追加コストを回避する保険。

## ドキュメントのメンテナンス

- MUST 変更後に README.md を確認し、正しい仕様を反映する
- MUST コマンド例、オプション、使い方の説明が正確であることを確認する

## 個人ノートからチームへ出すとき、相手が知っているかを確かめる

発動条件: memory・個人ノート・自分だけが見ている作業メモから、チーム向けの文書（Issue、PR 本文、MTG メモ、チャット投稿）へ項目を書き出すとき。

自分の中では「残タスク」でも、相手には初めて聞く話であることがある。痕跡の無い項目を残タスク一覧に並べると、相手は文脈を持たないまま判断を求められる。一覧の中で 1 項目だけ唐突だと、他の項目の信頼も落ちる。

- MUST 出す項目ごとに、相手が既に知っているかを確かめる。判定は「Issue / PR / ADR / コミットのどこかに痕跡があるか」。痕跡が無いものは、背景を 1 行添えるか一覧から外す
- MUST 痕跡の有無は `gh` や `git log -S` で確かめる。「たぶん共有した」で判断しない
- MUST 相手のコード・コメント・設定に由来する項目は、誰がいつ書いたかを添える（`git log -L <行>,<行>:<path>` で分かる）。出所が付けば唐突にならない
- SHOULD 自分だけが拾う雑務は、チーム向けの一覧に混ぜない。出すなら PR 本文に書く。変更そのものが文脈になる

なぜ効果があるか。共有物は、相手が読んだ時点の知識だけで判断される。書き手の頭の中にしかない前提は、読み手には存在しない。前提を補うコストは 1 行、補わなかったときのコストは「これは何の話ですか」という往復 1 往復分になる。

関連: `memory-hygiene.md`（memory に何を書くか）

## 自分の環境にしかないものをチーム向けの文書に書かない

発動条件: Issue、PR 本文、PR コメント、チャット投稿など、チームの他メンバーが読む文書を書くとき。

読み手は書き手と同じ道具を使っていない。手元の AI アシスタント、AI アシスタントの設定ファイル、独自のスラッシュコマンドや skill、ローカルのディレクトリ構成は、読み手の側に存在しない。名前を出しても伝わらず、「何の話ですか」と聞き返す往復が 1 回増える。

- MUST 手元の道具の名前をチーム向けの文書に書かない。対象は AI アシスタントの製品名、スラッシュコマンド、skill、ローカル設定ファイル、個人の作業ディレクトリ。書くのは検証の中身だけにする（「レビュー用のコマンドを通した」ではなく「何を確認して、何が分かったか」）
- MUST 読み手が見ていないコードについての記述を残さない。PR を出す前に自分で見直して直した分は、読み手にとって最初から存在しないコードなので、件数を書いても判断材料にならない
- SHOULD 環境の名前を出す必要があるときは、読み手が自分で確かめられる形にする。OS とバージョン、CI のジョブ名、リポジトリに入っているスクリプトのパスなら、読み手の側にも同じものがある

なぜ効果があるか。チーム向けの文書は、読み手が持っている知識だけで読まれる。書き手の環境にしかないものは、読み手にとって固有名詞ですらなく、意味の無い文字列になる。削るコストはゼロで、残したときのコストは説明の往復 1 回ぶん。

関連: `privacy.md`（固有情報の持ち込み防止）
