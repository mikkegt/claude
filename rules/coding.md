# コーディングスタイル

## 哲学

- YAGNI: 今必要ないものは作らない
- KISS: シンプルさを最優先する
- DRY: 同じコードを繰り返さない
- コンパクトな関数: 一目で全体を把握できる小さな関数に分割する
- 明確な命名: 関数名・変数名でストーリーが伝わるようにする
- 最小スコープ: 変数のスコープをできるだけ小さく保つ
- 読みやすい流れ: コードが物語のように読めること
- 最新のベストプラクティス: 非推奨（deprecated）の書き方を避ける

## ルール

- MUST 関数は20行以内に収める。超える場合は分割する
- SHOULD 読みやすい場合は命令型ループより関数型アプローチを優先する
- SHOULD コールバックチェーンより `async/await` を優先する
- NEVER マジックナンバーは使わない。名前付き定数を使う
- SHOULD 変数名に単位を含める（例: `timeout_ms`, `distance_km`）
- SHOULD 既定はコメントを書かない。命名・型・引数構造で伝わるようにする
- NEVER WHAT（何をしているか）を説明するコメントは書かない。良い命名と型で置き換える
- SHOULD WHY が非自明なときだけコメントを書く（隠れた制約、微妙な不変条件、特定バグの回避、ライブラリの癖、読者が驚く挙動）
- NEVER コメントに「現在のタスク」「該当 issue 番号」「呼び出し元」等を書かない（PR 説明や commit message に置く。コードから浮いて陳腐化するため）
- NEVER 複数段落のコメントブロックを書かない（外部契約の JSDoc 等の例外を除く）。1 行が上限
- SHOULD リファクタ時、WHAT コメントは積極的に削除する（コードが真実の源）
- MUST 失敗しうる操作には try/catch をつける
  - ネットワークリクエストにはタイムアウト処理を含める
  - コンテキスト付きの意味あるエラーメッセージを提供する
- MUST 上限が分かっていないファイルを丸ごと読まない。Node の `fs.readFile(file, "utf8")` は中身に関係なく約 512MB（V8 の最大文字列長）で throw し、囲んだ catch が「中身なし」と報告するので、最大かつ最もよく使われるデータが最も空に見える
  - 読みを足す前に 3 つ答える: 誰が書くファイルか（危険なのは「大きいファイル」ではなく、管理外のプロセスが追記し続けて上限が無いファイル）、上限はあるか（件数制限・ローテーション・TTL）、無いなら何が必要か（末尾だけなら範囲を区切って読む / 全件の集計なら行単位でストリームして畳む / クライアントに返すならサイズ上限と明示的なエラー）
  - MUST 窓で読むときは、元の関数に小さい入力を渡す。「新しい方から X 件を畳む」は元のルールの言い換えにならず、フォールバックやレコードをまたぐ意味が落ちる。窓サイズは実データで測る（1 レコードが巨大なことがある）

## デバッグの方針

- MUST 修正を試みる前に根本原因を特定する
- NEVER 場当たり的な修正（ハードコーディング、回避策）は使わない
- MUST リグレッション調査時はgit履歴/diffを確認する
- MUST デバッグに飛びつく前に、ユーザーの意図を理解する
- MUST 報告が本物か（再現するか、到達可能か、そもそも間違った挙動か）を修正の設計前に確定する。詳細は `debugging.md` を読む

## テスト

- MUST コード変更後はテストを実行し、既存テストが壊れていないことを確認する
- SHOULD テスト駆動開発（TDD）で進める
- MUST 外部API・サービスはモックする
- MUST ユニットテストでは以下のパターンを網羅する:
  - Happy path（正常系）
  - Edge cases（境界値付近・異常な入力）
  - Empty/null cases（空文字列、空配列、null/undefined相当）
  - Error cases（異常系・例外発生）
  - Regression tests（過去のバグの再発防止）
- SHOULD テストファイルはソースと分離して配置する
- SHOULD CIでテストを自動実行する
- MUST 判断と I/O を分ける。ルール（フィルタ、順序、上限、検証、整形、保持期間）は独立ファイルの純粋関数に置き、呼び出し元がファイル読み・プロセス起動・ソケット・HTTP を持つ。アプリを起動しないと届かないルールはテストされない
- MUST 純粋にできない境界は DI にする。`now()`、ID 検証関数、ファイルパス等を引数で渡す。import 時に時計やホームディレクトリやプロセスを束縛するモジュールは、開発者のマシンに触らずにテストできない。テストの都合ではなく設計上の欠陥
- MUST 新しいテストが、覆っているコードを壊したときに赤くなることを確認する。条件を反転する / ガードを消す / 修正を戻す → 赤を見る → 元に戻す。壊れたコードでも通るテストは別の何かを検証している。頻繁に起きるうえ、確認しない限り見えない
- MUST 呼び出し元も壊して確認する。ルールを抽出して網羅的に覆っても、証明されるのはルールだけで、呼び出し元が今もルールに到達しているかは証明されない。呼び出し元を壊して何も赤くならないなら、抽出はコードをテストの射程の外へ出したことになる
- SHOULD 何から書くか迷ったら、静かに失敗する順に並べる。throw する関数は自分で報告している。もっともらしい誤った値を返す関数（添字の off-by-one、バイト長と文字長の取り違え、誤った日付、拡張子の大小、緩すぎる検証、prototype chain を読んでしまう lookup）は、ユーザーがおかしなデータに気づくまで見えない
- SHOULD 意図的な非対称や既知の制限はテストで固定し、理由をコメントに書く。記録しないと次の読者が「直す」
- SHOULD monorepo では、テストがパッケージ名（ビルド済み dist に解決される）経由で import しているかソースパス経由かを確認する。パッケージ名経由ならソースを編集しても再ビルドまで何も変わらず、壊して赤くなるかの確認が意味を失う
- NEVER 「挙動を変えないリファクタだから」をテストを書かない理由にしない。コードを移動しても、中のルールについては何も証明されない
