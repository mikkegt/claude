# 一次情報の確認（「実装済み」と書く前に読む）

グローバル CLAUDE.md の「推測で仕様を語らない。実装コード等の一次情報で検証する」の
具体化。原則だけだと「行番号を添えれば読んだ気になる」という破り方が残るので、そこを塞ぐ。

発動条件: 既存コード・docs・過去の合意の状態を断定する文を書くとき
（設計メモ、PR 本文、Issue コメント、ユーザーへの回答すべて）。

## MUST

- 「実装済み」「対応済み」「〜になっている」「既に〜する」と断定する前に、該当箇所を
  Read して中身を引用する。ファイル名と行番号を添えるだけでは確認したことにならない
- 引用は該当行だけで終わらせない。条件分岐なら、その分岐が「何を拾って何を素通しするか」
  が分かる範囲まで読む（片方の条件だけ処理して残りは別扱い、というコードは多い）
- 過去の合意を根拠にするときは、出典（docs のパス、Issue/PR 番号）を示す。記憶や
  memory の記述だけを根拠にしない。memory は書かれた時点のスナップショットで、
  現在のコードとずれている可能性がある
- 確認していない箇所は「未確認」と明示する。断定と推測を同じ文体で並べない

## SHOULD

- 設計を語る前に、関連キーワードで docs / 過去 PR / Issue を横断 grep する。過去に
  議論・決定した内容が眠っていることが多い
- ユーザーに「これで合ってる?」と聞かれたら、引用を並べる形で返す

## OS / ランタイム依存の挙動は、本番と同じ環境で測る

開発環境で 1 回測った結果を「そういう仕様」と一般化しない。カーネル・libc・ランタイムの
実装差で、同じ API が逆の結果を返すことがある。しかもエラーにならず静かに割れるので、
片方だけ見ていると気づけない。

- MUST 挙動を根拠に判断するとき、その結果が **どの環境で measured か** を必ず併記する。
  本番 / 提出 / 評価環境が手元と違うなら、そちらでも測るまで結論を確定しない
- MUST 片方の環境でしか測っていないなら「未確認」と明示する。両方測って一致した場合だけ
  「そういう挙動」と書いてよい
- SHOULD 差が出たら man / 仕様書の該当記述を探す。仕様として明記されているのか、
  実装依存なのかで、回避策の寿命が変わる

## なぜ効くか

誤認は 1 箇所では終わらない。設計メモの「(既に X で実装済み)」という 1 行が誤りだと、
それを前提に実装がスキップされ、PR 本文にも転記され、レビューで指摘されるまで
気づかれない。読むコストは数十秒、伝播した後の手戻りは数日単位になる。
