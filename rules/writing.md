# ライティング（人間向け出力の軽い既定）

ユーザーへの回答・PR 本文・コミットメッセージ・コメント・人間向け docs に薄く適用される既定。

- SHOULD bold を多用しない。強調が本当に要る箇所だけ。
  箇条書きの項目名は太字にしない（例: `**速度:** 大幅に改善` → `速度: 大幅に改善`）
- SHOULD PR 本文・コミットメッセージ・PR コメントでは、原則 bold を使わない
- SHOULD Claude が読む設定ファイル（rules/ 等）では bold は使わない（実効が無い）
- SHOULD 過剰なヘッジングを避ける。言い切れるところは言い切る
- SHOULD 「重要です」「不可欠です」等の過剰な強調を削る

## 改行

- MUST 文章を 80 桁などで折り返さない。段落は改行を入れずに 1 行で書く
- MUST 対象は人間が読む文書すべて。PR 本文・PR コメント・Issue 本文・コミットメッセージ・docs・レポート・memory・設計メモを含む
- MUST 既存ファイルに追記するときは、そのファイルの行長を確認してから合わせる

折り返さない理由。日本語は単語境界が空白で示されないので、折り返し位置が語や文節の途中に来て読みにくくなる。1 語直すと行全体が diff に出るため、レビューで何が変わったか読み取りにくい。markdown では単一改行がレンダリング時に無視されるので、折り返しても表示は変わらず、エディタで読む人だけが損をする。

コードの整形規約（`.clang-format` の `ColumnLimit` 等）を文章に適用しない。適用対象はコードだけ。

## 使わない語彙

MUST 下表の語を使わない。レポート・PR 本文・報告書・MTG メモなど、人間の読み手に
届く文章が対象。会話内での使い捨てと、コード内の識別子・文字列は対象外。

| 使わない | 代替 |
|---|---|
| 本丸 / 本丸版 | 指す対象を具体名で書く |
| 宿題 | 持ち帰った項目、次回以降の検討事項 |
| 素直 | 単純 |
| 推し | 推奨 |
| 踏襲 | 引き継いでいる、そのまま使っている |
| 模倣 / 真似ている | 同じ形にしている、寄せている |
| 初出 | 最初に出てきた、初めて書かれた |
| 観察（体言止め） | 見えた、確認した |
| 留意 | 気をつける |
| 副次的 | あわせて、もう一つの |
| 本検証 | 今回の検証 |
| 概ね | ほとんど |
| 合意する | 決める、まとまる、すり合わせる |
| 浮き彫りにする | 分かった、見えた |
| 示唆しています | と読める、かもしれない |
| 効く / 効き / 効いている | 効果がある、効果があった |
| 追補 / 補遺 | 何を足したのかを具体名で書く（「測り直しと追加測定」など） |
| 当てる / 当たる（正解の意味で） | 選ぶ、対応づける、特定する、正解する |

表に載せているのは実際に指摘を受けた語だけ。新たに指摘されたら、使わない語彙表に足す。

チェック用 grep:

    grep -nE "本丸|宿題|素直|推し|踏襲|模倣|真似|初出|留意|副次的|本検証|概ね|合意|浮き彫り|示唆|効く|効き|効いて|追補|補遺|当てる|当たる" <対象ファイル>

## 見出しと、本文からの参照

- MUST 本文で「6 章」「3.7 節」と参照するなら、見出しにも同じ語を入れる（`## 6 章 タイトル`、`### 3.7 節 タイトル`）。見出しが `## 6. タイトル` なのに本文が「6 章」だと、読み手は探しているものを見つけられない
- MUST 参照の単位は文書内で統一する。章・節・項を混ぜない
- SHOULD 書き終えたら、本文の参照と見出しを突き合わせる（`grep -oE "[0-9]+(\.[0-9]+)? ?(章|節|項)" <対象ファイル>` で参照を洗い出し、見出しの表記と一致するか見る）

## 同じ主張を繰り返さない

長さそのものは問題ではない。読みにくくするのは、1 つの主張を言い換えて何度も書くこと。「簡潔に」を指針にすると、削るべきでない情報まで削って言葉足らずになる。削る対象は重複であって、情報ではない。

- MUST 1 つの主張は 1 箇所で書く。言い換え・要約・念押しで同じことを二度書かない
- MUST 相手が書いた内容（指摘、質問、依頼の文面）を説明し直さない。応答だけを書く
- SHOULD 段落の冒頭と末尾が同じことを言っていたら、どちらかを消す
- SHOULD 結論を書いた後、同じ結論を別の言葉で確認する文を足さない

チェック方法。各段落を 1 文に要約して並べ、同じ内容の行があれば統合する。

## 主語と、指す対象

文書は単独で読まれる。読み手は書かれた会話にいなかった人か、時間が経ったユーザー本人か、
新しいセッションの Claude。書いた本人だけが参照を解決できる状態にしない。

- MUST 主語を書く。「〜されている」「〜が判明した」で終えず、誰が何をしたのかを書く。
  自分（Claude）とユーザーがやったことを、第三者がやったように書かない
- MUST 「決まっている」「変更している」「〜になっている」のように、主体を言わずに状態だけ述べない。誰が決めたか・変えたかを書くか、状態の記述そのものを落とす。落とすかどうかは読み手が誰かで変わるので、先に読み手を確かめ、その読み手が既に知っていることなら文ごと消す
- MUST 独自のラベル・略語（章番号、案 A、検証 3、タスク記号）は、文書内で最初に
  使うときに何を指すか書く。定義せずに使わない
- MUST 数字を単独で置かない。「1/4 → 4/4」のような値は、何の母数で何を数えたかを添える
- SHOULD 抽象的な言い換えで済ませない。「対応した」「改善した」ではなく、何をどう
  変えたのかを書く

## 日本語では指示語を使わない

- MUST 日本語の文章では指示語を使わない。指す対象が同じ文書の中にあっても、具体名で
  書く。「指す先が直前の文にあるから可」という判断はしない
  対象: これ / それ / あれ / この / その / あの / これら / それら / こちら / そちら /
  そのもの / このうち / 前の / 先ほど / 上記 / 後述 / 前章 / 同様に
- MUST 置き換えは名詞を具体名にする。「この質問」→「振り返り応答が作る質問」、
  「これらが」→「#739 と #742 が」、「この指標」→「深さの指標」
- MAY 直後の表・箇条書き・コードブロックを指す「次の」「以下の」は使ってよい。
  指す先が同じ画面にあり、間に別の対象が入らない
- MAY 「そこで」「そのため」は接続語で指示語ではない。ただし「代わりに」「だから」で
  置き換えられるなら置き換える

なぜ日本語だけ厳しくするか。英語の技術文書のルールは「指示語を使わない」ではなく
「名詞を伴わない裸の this を使わない」で、this feature や this metric は許される。
冠詞と単複があるので、the question と書けば文法だけで直前の対象を指せて、数が合わない
参照は書いた時点で壊れて見える。日本語には冠詞も単複の区別もないので、「この質問」が特定の
1 つを指すのか質問全般を指すのか、語彙だけでは決まらない。指示語を足して補ったつもりが
新しい曖昧さになる。一方、名詞の反復に対する許容度は日本語のほうが高いので、指示語を
全部外しても読みにくくならない。英語より厳しい規律にするのは、冠詞と単複の差を埋めるため。

書き終えたら洗い出す。ヒットは原則すべて具体名に直す:

    grep -nE "これ|それ|あれ|この|その|あの|こちら|そちら|そのもの|前の|先ほど|上記|後述|前章|同様に" <対象ファイル>

語彙表と違い、ヒットしたものが全部悪いわけではない（「そのため」「次の」等）。読んで判定する。
